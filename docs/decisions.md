# Decisions

Decisions behind this repository and its rules, settled by the owner in a planning interview on 2026-11-10. One row per decision; a reversal is a new row that names the one it replaces.

Plain text in the Reason and Chosen against columns is the owner's; *italics* are the author's summary where the interview did not state one.

| ID | Decision | Reason | Chosen against |
| --- | --- | --- | --- |
| D1 | The shared rules live in a public repo, `Tonttu84/ai-workflow`, cloned locally; the user-level `~/.claude/CLAUDE.md` is one line importing `rules/working-agreements.md`. | Every session on the machine loads the same rules. | *Copying the rules into each project.* |
| D2 | Personal and machine-specific details (paths, accounts, OS quirks) stay out of this repo, in local memory. | The repo is public. | — |
| D3 | Each project's rulebook is `AGENTS.md`; its `CLAUDE.md` is `@AGENTS.md` plus Claude-only extras if any. `AGENTS.md` holds only project specifics (kind, stack, commands, domain rules, quirks) and points to the shared rules. | `AGENTS.md` is the open standard other coding tools read. | *A `CLAUDE.md`-only setup.* |
| D4 | The main conversation coordinates (plans, grills, briefs, reviews, merges); coding, long test runs and review fixes go to subagents with a complete, self-contained brief: files to touch or avoid, tests first, verification, what to report. | *Keeps the coordinator's context for decisions; a written brief makes the work checkable.* | *The coordinator writing the code itself.* |
| D5 | Coordinator model: Fable 5.1. | The owner's choice. | — |
| D6 | Subagents default to Opus 5.5 at normal effort, through `CLAUDE_CODE_SUBAGENT_MODEL` in the user settings. | *Strong enough for most coding work, at a lower cost than the coordinator's model.* | *Inheriting the coordinator's model.* |
| D7 | Forks are denied (`Agent(fork)` in `permissions.deny`). | A fork runs on the coordinator's model, bypassing D6. | — |
| D8 | The coordinator escalates on its own judgement to Opus or Fable at high effort for a hard task, and explains in detail why the task is hard for an AI, in the chat and in the public `escalation-log.md`, adding afterwards whether the escalation was needed. | The owner wants to learn what AI finds hard. | *Escalating silently.* |
| D9 | The pinned session model (`"model": "haiku"`) is removed from the user settings. | *The coordinator model is chosen per D5.* | — |
| D10 | Grill before building when confidence is not high: one question at a time, each with a recommended answer. | Staying aligned with the owner outranks moving fast. | *Building on assumptions.* |
| D11 | A new project starts with a grill and a `docs/kickoff.md` written before any code: goal, kind (solo or showcase), the stack decision with the alternatives considered, the first decisions, the agent brief. | *Decisions made before code are cheap to change.* | *Starting from code.* |
| D12 | The stack is discussed at every kickoff. Default proposals: web app in TypeScript (strict), Next.js, Tailwind, Prisma, Zod, Vitest, Playwright; compiled work in Rust first, C++ when the project needs its libraries, an engine or embedded toolchains; Python (uv, FastAPI, pydantic, pytest, ruff) for services, scripts and data work. | Rust: the owner is learning it, and a strict compiler is a fast reviewer for agents. C++: the owner knows it from school. | Python as the default when the project would benefit from a compiled language. |
| D13 | Every project keeps `docs/decisions.md` (D-number, decision, reason, chosen against). No time logs in new work; projects that already keep them may keep their own rule. | The owner's choice: "decisions only". | Time logs in new work. |
| D14 | Test first for domain logic and every bug fix (a failing test first); UI gets behaviour tests (end-to-end, layout checks) written with the change. | *A failing test proves the test can catch the bug.* | *Tests written after the code.* |
| D15 | After each feature lands, a separate agent that did not write it attacks its tests (edge cases, property tests, "would a wrong line still pass?"); findings become a follow-up change. | *An author tends to test only what they already thought of.* | *Relying on the author's tests alone.* |
| D16 | Automated pass/fail checks over an agent or a human eyeballing results. Tests are never weakened, skipped or deleted to go green. Logic pure, IO at the edges; no network in unit tests. | *Repeatable, honest checks.* | An agent or a human eyeballing results. |
| D17 | Git flow by project kind, stated in each `AGENTS.md`: solo projects commit to `main` and push once the gate is green; showcase or team projects use branch, PR, fresh-agent review and squash-merge on the owner's word. | *Solo work stays fast; showcase work shows a team workflow.* | *One flow for every project.* |
| D18 | Fresh-agent review on every PR and, on solo projects, on every non-trivial change before the push. The reviewer has none of the author's conversation, reads the diff cold and posts its verdict (`gh pr review --comment` where there is a PR); the author fixes; a fix beyond a finding is re-reviewed. | *A cold reader catches what the author cannot see.* | *Self-review only.* |
| D19 | Commit style: Conventional Commits plus good-message rules. Subject `type(scope): imperative summary`, at most 72 characters; a body that says why, wrapped at 72; one logical change per commit. Types: feat, fix, docs, test, refactor, perf, build, ci, chore, revert. | *Readable history that tools can parse.* | Task ids (like R99) in the subject; they go in a `Refs:` footer. |
| D20 | The commit style is enforced by a hook in every project: commitlint and husky in Node projects, the portable `hooks/commit-msg` from this repo elsewhere, installed by the project's setup command. Never `--no-verify`. | "You fight how you train." | *Rules on paper only.* |
| D21 | Parallel agents use one worktree per task and merge sequentially; check the branch and fetch `main` before the first commit. | *Agents do not overwrite each other's work.* | *Sharing one checkout.* |
| D22 | The grill skill tracks the latest upstream (mattpocock/skills), installed once at user level, keeping the owner's local "proactive" clause while it is still needed; the per-project copies are removed. | The copies diverged by timing, not on purpose. | A frozen copy; a copy in each project. |
| D23 | All active projects move to these rules now, one agent per project, each following that project's own landing rules. Inactive, course and other people's repositories are not migrated. | *One way of working everywhere.* | *Migrating each project when it is next touched.* |
| D24 | The grill skill overlay also tells the skill to ask one question per message. Confirmed by the owner on 2026-11-10: one question at a time keeps them focused. | Upstream moved from one question at a time to rounds of numbered questions after the local copies were made; D10 asks one at a time. | Following upstream's rounds (drop `skills/overlays/grilling/append.md` to switch). |
| D25 | Commits in this repo use the GitHub handle and its noreply address. Agent's choice. | D2: no personal details in a public repo, commit metadata included. | The machine's global git identity. |
| D26 | `hooks/commit-msg` ignores comment lines (and cuts at the scissors line) only where git does. When git exports `GIT_EDITOR=:` to the hook, no editor ran (`-m`, `-F`, `--no-edit`): comment lines count unless `commit.cleanup` is `strip`. Otherwise the editor ran, or the hook runs by hand: git's English template text decides ("will be ignored" or "will be kept"), else `commit.cleanup` (strip unless whitespace, scissors or verbatim). A `--cleanup` option on the command line is not visible to the hook. Agent's choice under the owner's "fix all", after cold reviews on 2026-11-10. | *The hook must check the message git saves. Dropping `#` lines always let `-m $'# x\nfeat: ok'` through; the template text alone fails under a translated git and with `--no-status`. `GIT_EDITOR=:` is how git itself tells a hook that no editor ran (checked end to end in the tests).* | *Always dropping comment lines; the template text as the only signal.* |
| D27 | The hook counts subject characters by dropping UTF-8 continuation bytes under `LC_ALL=C`, in every locale. Agent's choice. | *One code path gives the same count everywhere; `${#subject}` counted bytes under `LC_ALL=C` (60 "ä" counted as 120).* | *Trying a UTF-8 locale first and falling back to the byte count; locales differ between machines.* |
| D28 | `hooks/install.sh` in its default mode refuses when `.git/hooks` holds any hook other than `.sample` files and the hook itself, while no `core.hooksPath` is in effect; `--force` overrides. It warns, without refusing, when it overrides a global or system `core.hooksPath`. Agent's choice of the details, after a cold review on 2026-11-10. | *Setting `core.hooksPath` silently switched off pre-commit, husky, lefthook and Git LFS hooks. When a hooks path is already in effect, `.git/hooks` is ignored anyway, so there is nothing new to switch off.* | *Taking over silently; chaining to the old hooks from `.githooks/`.* |
| D29 | Skill overlays can replace exact text in any file of a skill (`replace.txt`), and the sync fails when upstream no longer has the old text. The grilling overlay uses it to make `agents/openai.yaml` say "one question at a time" (D24). Agent's choice. | *The vendored file contradicted D24, and vendored files are never edited by hand. A text replacement keeps the rest of upstream's file and stops the sync when upstream rewords it.* | *Editing the vendored file by hand (lost on the next sync); excluding the file (loses upstream's metadata); shipping a whole replacement file (hides upstream changes).* |
| D30 | Node projects may use commitlint and husky instead of `hooks/commit-msg`; they are not required. `templates/commitlint.config.mjs` makes commitlint accept and reject the same messages as the hook. The "may" is the owner's choice (2026-11-10); the matching config is the agent's choice under the owner's "fix all". Replaces the Node clause of D20. | *The rules said "must", the readme and installer "may"; one hook that works everywhere is enough, and a matching config keeps the choice free.* | Requiring commitlint and husky in every Node project. |
| D31 | The PR title is the squash commit's subject and follows the commit format. `templates/commit-check.yml` checks it on every pull request with the project's committed hook taken from the base commit, rejects titles the hook would exempt as git's own messages, and fails on `fixup!`, `squash!` and `amend!` commits in the PR. GitHub's repository setting `squash_merge_commit_title=PR_TITLE` is required, since by default a one-commit PR's squash subject is that commit's subject. Agent's choice under the owner's "fix all", 2026-11-10. | *Nothing checked the subject that lands on `main` after a squash merge, and the hook lets fixup subjects through.* | *The hook from the PR's own head (a PR could weaken its own check); a third-party marketplace action.* |
| D32 | Repositories the owner does not own (course work, other people's projects) and the owner's inactive ones left unmigrated (D23) get a fallback: follow their own conventions, never push without asking, skip the kickoff, commit-hook and escalation-log rules. Any other repository of the owner's without an `AGENTS.md` gets the kickoff or a migration. Agent's choice under the owner's "fix all", 2026-11-10. | *D23 leaves such repositories unmigrated and the rules had no fallback. Keyed on ownership, not on a missing `AGENTS.md`, so this repository and the owner's new projects before kickoff are not caught.* | *Keying the fallback on a missing `AGENTS.md`; applying every rule everywhere.* |
| D33 | An escalation-log entry is committed with `git pull --rebase --autostash` first and `git commit -- escalation-log.md` (that file only), then pushed, pulling again when the push is rejected; the file merges with `merge=union` (`.gitattributes`) so two appended entries never conflict, and outcomes are appended as new lines rather than edited into entries, since a union merge would keep the stale copy too; project details in it stay generic. Agent's choice under the owner's "fix all", 2026-11-10; refines D8. | *Sessions in every project push to this repo's `main`: without the pull they race, a broad `git add` could sweep up the owner's uncommitted edits, and the file is public.* | *Committing and pushing as before.* |
| D34 | A test that looks wrong: the subagent stops and reports why; the coordinator then fixes it as its own change. Agent's choice under the owner's "fix all", 2026-11-10. | *The rules said "fix it", the agent brief "stop and report"; a subagent changing the test it must pass is the risk.* | *Letting the subagent fix the test itself.* |
| D35 | Every command an agent runs has a time limit: the tool's timeout, `timeout` (or an equivalent) around commands that might hang, background jobs with a deadline instead of endless polling, loops with an exit condition and an iteration or time cap, and no interactive prompts (non-interactive flags). Owner's choice on 2026-11-10; extends the deadline rule of the working agreements. | So a mistake in a shell command cannot leave an agent stuck looping forever. | *Deadlines only for network calls, polling loops, test waits and CI jobs.* |
| D36 | Owner's choice on 2026-11-10: CI checking every commit message is the gate; the local hook is feedback while writing; a ruleset makes the gate binding, and on GitHub Free, where rulesets work only on public repositories, private repositories are a recorded exception (the check is visible, not blocking) until the plan changes. Agent's choice under that decision: the mechanics in `templates/commit-check.yml` (every commit of a pull request and of a push to `main`, the PR title, the hook taken from the commit before the change, the fallbacks for a new hook, a new branch and a lost old tip). | The local hook is local config a clone does not copy; `--no-verify` and GitHub's web editor skip it, and squash merges write their commit on GitHub. | *The local hook as the only check.* |
| D37 | Every project gets Dependabot: security updates on in every repository, version updates from `templates/dependabot.yml`, one grouped pull request per ecosystem with `chore` and `ci` (actions) prefixes, short enough that the title still fits 72 characters after a squash merge appends " (#N)", `github-actions` always. Repositories with nothing to update skip version updates. Updates run on the 1st and 15th of each month everywhere: owner's choice on 2026-11-10 ("1st and 15th is fine"), as Dependabot has no two-week interval; the template uses `interval: cron` for it. The rest of the template (groups, prefixes) is the agent's choice under that decision. | *Actions are pinned by SHA and only move through Dependabot; batched updates keep everything current without a stream of pull requests, and the prefixes and short group names keep each title within the commit check.* | *Weekly updates (lease-loop's setting); monthly.* |
| D38 | Solo repositories get a ruleset that blocks force pushes and deletion of `main` but does not require the commit check; CI stays visible there. Repositories that work through pull requests require the check. Owner's choice, confirmed on 2026-11-10 (first proposed by the coordinator under D36). | *A required check rejects direct pushes, which would break the solo flow (commit to `main` and push) and the escalation-log pushes to this repository.* | *Requiring the check in every repository.* |
